This is actually a good starting structure. Given that you want **one Git repo shared by HPC + local desktop, with rclone for data**, I would make a few structural changes now before the project gets larger.

Your current structure is:

```text
xenium_lung/
├── code/
│   ├── xenium_5k/
│   └── xenium_v1/
└── data/
    ├── bundle/
    ├── spatialdata/
    └── table/
```

The main issue is that **`code/` and `data/` are currently mixed conceptually**: some things are source code, some are notebooks, some are environments, while all data are under one directory. That's manageable now, but will become harder when you have multiple Xenium samples and downstream results.

## What I would use

I'd change it to:

```text
xenium_lung/
│
├── README.md
├── .gitignore
│
├── code/                         ← Git
│   ├── xenium_5k/
│   │   ├── 01_data_analysis.ipynb
│   │   ├── 02_downstream_analysis.ipynb
│   │   ├── create_spatial_data.ipynb
│   │   └── environment.yml
│   │

│   │   ├── 02_transcript_viz.ipynb
│   │   ├── 03_viz_cell_zarr.ipynb
│   │   └── ...
│   │
│   └── scripts/
│       ├── export_for_napari.py
│       └── ...
│
├── data/                         ← NOT Git
│   ├── raw/
│   │   └── xenium_5k/
│   │       └── bundle/
│   │
│   ├── spatialdata/
│   │   └── xenium_prime_5k.zarr
│   │

│   │   └── visualization/
│   │

    └── ...
```

### Why this is better

The distinction becomes very clear:

**`code/`** → things you write
**`data/`** → things you analyze
**`results/`** → things your analysis produces
**`config/`** → parameters/settings
**Git** → code/config
**rclone** → data/results

# 6. Your rclone structure

This is where your setup becomes really nice.

I would create a Google Drive structure like:

```text
gdrive:Projects/xenium_lung/
│
├── data/
│   └── raw/
│
├── spatialdata/
│
└── results/
    └── visualization/
```

But you don't necessarily have to mirror everything.

For example:

### HPC → Google Drive

```text
HPC
results/xenium_5k/visualization/
          │
          │ rclone
          ▼
Google Drive
results/xenium_5k/visualization/
```

### Google Drive → local

```text
Google Drive
results/xenium_5k/visualization/
          │
          │ rclone
          ▼
Local
results/xenium_5k/visualization/
```

So the **large raw Xenium data never needs to touch your local machine**.

Because you're doing **Xenium + spatial transcriptomics**, I would distinguish:

```text

results
visualization
```

rather than putting everything under `data`.

Eventually:

```text
xenium_lung/
│
├── code/
│
├── data/
│   └── raw/
│
├── processed/
│   ├── spatialdata/
│   └── matrices/
│
├── results/
│   ├── clustering/
│   ├── annotation/
│   ├── spatial/
│   └── visualization/
│
└── config/
```

That gives you a very clean conceptual pipeline:

```text
RAW
 │
 │ preprocessing
 ▼
PROCESSED
 │
 │ analysis
 ▼
RESULTS
 │
 │ export
 ▼
VISUALIZATION
 │
 │ rclone
 ▼
LOCAL NAPARI
```

For a project that will eventually contain **Xenium 5K, Xenium v1, multiple samples, cell-type annotation, TME analysis, spatial neighborhoods, and figures**, I think this organization will scale much better than your current `data/bundle + data/spatialdata + data/table` layout.

**Most importantly, I would not move files manually yet.** First establish the Git/rclone rules and directory structure; then we can write the two small rclone scripts around the exact paths on your HPC and local desktop.
